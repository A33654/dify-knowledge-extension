# 2026-10-26 Dify 文档上传接口异步化改造

## 需求

# 2026-10-26（追加）删除文档/知识库的缓存失效：调研结论（未落盘）

## 两条删除链路落点
- `services/knowledge/dataset_service.py:1947` `DatasetService.delete_document(document, session)`（staticmethod），
  发 `document_was_deleted` 信号 → `session.delete(document)` → `session.commit()`。
- 同文件 `:1966` `delete_documents(dataset_ref, document_ids, doc_form, session)` 批量版，
  commit 后 dispatch `batch_clean_document_task`。
- `:1262` `DatasetService.delete_dataset(dataset_id, user, session)`（staticmethod），
  发 `dataset_was_deleted` 信号 → 删 API key 绑定 → `session.delete(dataset)` → `session.commit()`。

## 决定性发现：删文档后缓存其实不可达
两个读接口都挂在 `/datasets/{id}/documents/{doc_id}/versions`，RBAC locator 是
`DatasetByDocument`（`controllers/common/rbac/locators.py:133`），它先
`get_dataset_id_by_document(tenant_id, document_id)`，为 None 就 `raise NotFound("Document not found")`。
**文档删掉后请求在准入层就 404，根本到不了缓存** → 方案A（只靠 300s TTL）实际无用户可见脏读。
注意：dataset 级 locator `DatasetId.locate` **不校验 dataset 是否存在**，只取路径参数，
所以「删知识库」这条的门禁比删文档弱，是唯一留口子的地方。

## Redis 前缀扫描：不可用（重要）
- `RedisClientWrapper` **没有** `scan`/`scan_iter`/`keys` 方法；只有 `:253` 的 `__getattr__` 兜底。
- 兜底调用**不会套 `REDIS_KEY_PREFIX`**，且全仓库 grep `scan_iter` **零命中**（无先例），
  RedisCluster 下语义还不一样 → 按前缀批量删要动 `ext_redis.py` 公共基础设施，风险高、不符合「不重构」。
- 结论：删 dataset 只能走「查 document_id/version_id 再逐个删」。可用 `redis_client.delete(*names)`（wrapper 已支持多 key）。

## 索引坑
`document_versions` 只有 `document_id`、`tenant_id`、`(tenant_id, dataset_id, business_key, version)` 唯一索引，
**没有单独的 dataset_id 索引** → 按 dataset 查版本必须带 `tenant_id + dataset_id` 才能命中复合索引，否则全表扫。

## 其他
- models/dataset.py 里 grep `ondelete=` / `cascade=` **全无命中** → 删 Document 不会级联删 DocumentVersion，
  删 Dataset 也不会级联删 Document，靠信号 + 异步任务清理。因此「缓存陈旧」永远不会超过「DB 陈旧」。
- 文档 id 是 uuid4，不会复用，不存在删后重建撞 key 的问题。

## 决策：选方案 A —— 删除文档/知识库不补缓存失效
用户拍板 A，代码**零改动**。理由：删文档后缓存被 `DatasetByDocument` 的 404 门禁挡住、不可达，
B 修的是当前观测不到的非 bug，却带来长期维护成本。翻转条件（合规「删除即消失」/ 新增绕过门禁的读路径）
已写入 `.workbuddy/memory/MEMORY.md` 供后续查阅。

## 技术判断（写进了方案）
- Celery 钩子职责：`on_retry` 触发时 `self.request.retries` **尚未自增**，用它计数会 off-by-one；
  `on_failure` 时已无重试决策空间；**只有 `__call__` 能包住 `self.retry()` 自身抛的异常**
  （broker 不可用 → 静默丢失）。故决策主体必须在 `__call__`，另两个只做幂等兜底。
  `self.retry()` 的三层 try 结构照抄 `ops_trace_task.py:132-142`。
- 78 个任务文件中 **20 个已自带** `max_retries`/`autoretry_for`，基类无条件接管会嵌套成 9 次重试
  → 必须 opt-in（kwargs 带 `task_execution_id` 才启用）。
- 退避口径：`countdown = 2 ** (retries + 1)`，max_retries=3 → 2/4/8s，共执行 4 次约 14s 后进死信。
- 最高风险是 **R2 重跑幂等**（未验证 `services/knowledge/indexing/` 是否按 document_id upsert）
  和 **R5 租户隔离队列标志**（`_document_indexing_with_tenant_queue` 的 finally 交互）。
- 未引入 AST 工具 → `batch_create_segment_to_index_task.py` 的 BOM 风险自动规避。

# 2026-10-26（追加）R2 索引幂等调研结论：**不幂等，禁止给索引任务加重试**

## 决定性原因
`core/rag/index_processor/processor/paragraph_index_processor.py:110-116` 里
`doc_id = str(uuid.uuid4())`（qa/parent_child/paragraph 三类 processor 全同）。
写入落点 `core/rag/docstore/dataset_docstore.py:67-186 add_documents` 是
**select-then-insert-or-update**（无 on_conflict_*）：先按 `index_node_id` 查，命中才覆盖更新。
**key 每次都是新 uuid → 第二次永不命中 → 走 insert → 行数翻倍。**
`models/dataset.py:558-568 DocumentSegment` 对 `index_node_id` 只有普通 index、**无唯一约束**。
向量侧：`vector_base.py:71-72` 向量 id == `index_node_id`；`load` 走 `Vector.create`
**从不传 duplicate_check**（只有 `Vector.add_texts` 有，`vector_factory.py:274-277`）→ 向量也翻倍。
`sement_repository.py:104-117` 还会把旧 segment 打回 `INDEXING` 但**不改 enabled**，
而检索按 enabled 过滤（`retrieval_service.py:485-487`）→ 旧行继续参与检索，双重污染。

## 为什么 `run()` 不清理
`services/knowledge/indexing/execution.py:105-140`：`_run` 只有 `start=="splitting"` 才
`clear_for_indexing`；**`start=="parsing"`（run() 默认路径）假定调用方自己先删了**。
全仓库唯一先删后插的地方是 `tasks/duplicate_document_indexing_task.py:135-166`。
反例：`recover_document_indexing_task.py:38-48` 的 waiting/parsing/cleaning 分支直接 `run()` → 翻倍
（另两个状态走 run_in_splitting_status / run_in_indexing_status，是幂等的）。

## ★ 第三层吞异常（比 R1 更深）
`services/knowledge/indexing/execution.py:132-138`：除 `DocumentIsPausedError` 外
`except Exception` 只 `fail_indexing` **不 raise** → `run()` 正常返回 →
`document_indexing_task._document_indexing` 的 `has_error` 保持 False → 任务标 SUCCESS。
**路线2 只改 document_indexing_task.py 补 raise 不够，必须连 IndexingService._run 一起改（两层）。**

- FlaskTask 只埋点不接管重试；三层 try 留在 document_async_task.py 内；on_retry/on_failure 不动

## 实现中定下的两个机制（写代码时容易踩）
- **task_execution_id 在 `__call__` 里剔除后再调 `self.run()`**：用
  `kwargs.get` + 字典推导过滤（不 pop，避免非 str 时误删），这样 `document_async_task(self, task_id)`
  签名不用改；重试时 `self.retry(kwargs={"task_id":..., "task_execution_id":...})` 重新带上。
- **埋点三方法都加 `status == PROCESSING` 守卫**：document_async_task 自己已写
  success/failed/dead_letter，钩子只在仍是 PROCESSING 时才写，避免状态互相覆盖。
  所以钩子实际是「任务自身处理不了就兜底」的安全网。
- controller 里 `with_session(write=True)` 是在 view 返回后才 commit 的，

  所以重试接口必须**自己先 commit** 再 apply_async（worker 要读已提交状态），
  投递失败时显式回写 dead_letter + commit（装饰器 rollback 撤不回已提交的）。
